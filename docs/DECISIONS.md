# Active Architecture Decisions

1. **Current-state documentation:** Markdown describes only the active implementation and binding rules. Git provides history.
2. **Closed applications:** The learner must not require target application source, private APIs, business databases, or runtime AI.
3. **Persisted Guides:** The database is the execution source of truth. The runtime, not a test driver, owns validation, completion, and Step advancement.
4. **Deterministic targets:** Resolve using persisted descriptors, anchors, and context. Reject missing or ambiguous matches.
5. **Runtime-neutral contracts:** Core and data abstractions remain independent of SQLite and platform adapters.
6. **Web adapter:** The production Web path uses GuideMe (Chrome extension), Native Messaging, named pipes, and .NET. No Playwright production dependency.
7. **Windows adapter:** The production Windows path uses UI Automation.
8. **Application contexts:** Resolve an explicitly identified application instance; do not infer identity from arbitrary target matches. Unsupported multi-context behavior must fail explicitly.
9. **Guide launch:** `GuideMe.exe --guide <GuideKey>` loads and compiles the V5 guide definition. Step advancement follows the persisted `StepAdvancePolicies` (`Manual` or `AutomaticOnValidation`); there is no separate runtime mode switch.
10. **Guide Steps:** Disabled Steps keep their identity; centered targetless Steps are valid; the example Guide's final summary is persisted rather than synthesized.
11. **Target ownership:** Guide completion and termination through the session-scoped GuideMe notification-area menu end the learner and clean its UI without closing the target application. The same Guide can be launched again.
12. **Demo/test separation:** SampleApp and test-specific drivers must not define product behavior. Example Guides are data, not special cases in runtime code.
13. **V5-only persistence:** The Learner and Native Host read guide definitions only from V5. The production database is `C:\ProgramData\GuideMe\Data\GuideMe-V5.db`; `GuideMe_DATABASE_PATH` selects a validated V5 database when explicitly configured. Do not add a parallel persistence format.
14. **Timeout policy:** Automated technical waits must not be increased beyond five seconds without explicit approval; human time spent on a Guide Step is not a technical timeout.
15. **Product naming:** The user-facing product and Chrome extension are named **GuideMe**. Existing internal executable, assembly, component and protocol identifiers retain GuideMe naming.
16. **Deployment:** `scripts/Publish-Customer-Package.ps1` packages the Windows learner, Native Messaging host, and Chrome extension. `scripts/Publish-GuideMe.ps1` updates the existing `C:\GuideMe` installation, publishing the Native Host into `C:\GuideMe\NativeHost` and synchronizing extension icons; `-SkipExtensionSync` supports isolated staging. The Chrome Native Messaging registration must resolve to `C:\GuideMe\NativeHost\GuideMe.NativeHost.exe`.
17. **Web transport lifecycle:** The GuideMe extension currently keeps a Native Messaging connection that may outlive Guide sessions. Do not introduce on-demand connection/disconnection without a reliable reactivation mechanism and regression coverage. An idle native host is not by itself a learner-process leak.
18. **Existing text values:** A text-input Step requires an observed focus-and-leave interaction before evaluating a pre-existing value. No text modification is required; persisted validation and completion conditions must still pass. The same rule applies to Web and Windows, without demo-specific checks.
19. **Instructor:** Authoring and AI-assisted diagnosis are future capabilities. Instructor write/edit operations must target V5 directly; the Learner does not depend on the Instructor or runtime AI.

20. **Dynamic captures:** A Guide may reuse values observed in earlier Steps through persisted capture definitions and locator/anchor tokens. Missing or ambiguous observations must not be guessed. The Instructor's UI and suggestion workflow for authoring these definitions remain undecided.

21. **GuideMe session control:** Web and Windows learner sessions share a single Windows notification-area control, created only while a Guide is active. The icon uses the embedded GuideMe extension artwork. Both a single left-click and a right-click open the same menu, showing the fixed heading **GuideMe** and an immediate **Exit** action ("יציאה" in Hebrew), without confirmation. Exit does not close the target app or browser. Neither bubble exposes an exit button. Windows controls whether the icon appears directly on the taskbar or in notification overflow. Keep the menu extensible for future Instructor actions; do not introduce a permanent tray agent. Keyboard and screen-reader behavior still requires dedicated verification.\n
22. **GitHub branch policy:** All development, fixes, and documentation updates are made directly on the existing `main` branch of `shabydevelop-code/DAP-Platform`. Do not create or use feature, temporary, or working branches, and do not open pull requests for routine changes unless the user explicitly changes this rule.
23. **Repository write failure handling:** If a GitHub repository write is blocked or fails, do not immediately declare the task failed. Re-read the current file and SHA, then retry the intended write once against `main` when the failure is transient or retryable. If the block is an explicit safety/policy denial, do not circumvent it or repeat an identical prohibited operation; report the exact limitation and leave the repository state unclaimed. Verify the returned commit before reporting success. Never silently substitute another branch.

24. **Learner UI localization:** Learner-facing text is obtained through the shared `IUiTextProvider` and the Hebrew/English catalogs. The fixed product name **GuideMe** is not translated. A lightweight precompile check in `GuideMe.App` validates translation parity and catches common hardcoded UI strings in selected learner entry points, reporting file and line; it is not an exhaustive analyzer. Keep the check within the existing build process, without separate CI workflows or broader test hardening.
25. **V5 identity and ordering:** Every Guide has a stable `GuideId` and `GuideKey`. Step identity is `(GuideId, StepId)`; `StepOrder` is an editable order field, not part of identity. Child entities use composite keys reflecting their ownership. The authoritative physical schema is `docs/schema/GuideMe-V5.sql`.
26. **Database change workflow:** The active V5 database is the execution source of truth. Do not create automatic backups or working copies unless explicitly requested. Make narrowly scoped, validated data corrections when authorized; do not globally rename historical Step IDs or capture references merely for cosmetic consistency.
27. **Verified learner scope:** The installed Learner is verified with the SampleApp Web Guide (55 Steps), Windows Guide (55 Steps), and mixed Web–Windows–Web Guide (6 Steps). These fixtures verify the product runtime; they do not define production rules.

28. **Instructor accessibility is a mandatory development rule:** Every new or changed Instructor view, dialog, field, picker, and workflow must preserve accessible keyboard-only operation, visible focus, logical focus order and return, semantic labels and headings, accessible error/status announcements, Hebrew RTL behavior, readable contrast, zoom/reflow, and screen-reader compatibility. Aim for WCAG 2.2 AA; never claim conformance without verification. Accessibility is a release requirement, not optional polish. Follow `docs/INSTRUCTOR_ACCESSIBILITY_AUDIT.md`; do not introduce Playwright or automated visual/browser UI tests without explicit approval. Do not trade away accessibility when simplifying or shrinking dialogs.
29. **Instructor step authoring:** Select the target application in both Add Step and Edit Step, including single-application guides. Prefer compact, content-sized authoring dialogs; avoid exposing manual bubble placement as a routine field. The desired end-state is one cohesive authoring flow for instruction, target selection, completion condition, and save, without requiring the author to understand internal locators. Preserve existing step mappings when changing application and warn when revalidation is needed.

30. **Instructor change observation (initial implementation):** A Web author may start a read-only before/after observation of the selected application tab. The Chrome extension periodically samples bounded visible, non-sensitive DOM IDs in each accessible frame and reports appeared/disappeared selectors. It must never prevent clicks, modify business events, or automatically choose or persist a completion rule. Findings are suggestions for the author to verify. This initial capability does not yet cover every DOM change, iframe navigation transition, Windows applications, or one-click conversion of findings into V5 StepRules; these require separate design and verification. The Learner remains independent of observation and AI.

## Instructor V5 — author-selected Web completion target (2026-10-24)
- The author selects a primary action target and may explicitly select one secondary Web target using the existing picker. The only new secondary rules are `target-appeared` and `target-vanished`; generic `changed` is deferred.
- The target can be selected before or after performing the action in the target application; the learner samples its state before inviting the learner to act. A condition already satisfied at baseline does not count as a transition.
- Additional rules persist as a distinct `StepTargets` usage and `StepRules` `AdditionalCompletionCondition`, not by overwriting the primary action or validation. Only one new secondary rule per step is supported by this editor; removal is explicit.
- The experimental automatic observation controls are hidden from the Instructor UI; the underlying diagnostic endpoints remain available for investigation.
- This is an initial implementation. A transient frame detach during navigation must not be interpreted as a permanent disappearance; the runtime rechecks after a short interval, but production validation of full reload, iframe reload, and SPA transitions is required before calling this fully regression-tested.

## Web completion visibility semantics (2026-10-24)
- Author-facing `target-appeared` / `target-vanished` mean rendered presence/absence, not merely DOM membership. The Learner inspects CSS visibility, hidden/inert ancestors, closed details, and layout rectangles in the selected frame. The author does not configure or inspect `innerHTML`.
- Existing `target-exists` / `target-not-exists` retain locator/DOM-resolution semantics for backward compatibility.
- A transition requires an opposite-state baseline before the learner acts; a target already visible at step entry does not count as newly appeared. Rechecking disappearance guards against brief frame detach. Production verification remains required for iframe refresh and fast transitions.

## Active learner session indicator (2026-10-24)
- The shared Web/Windows/mixed session indicator displays the localized active-status label and the human-readable V5 `Guides.GuideName`, resolved by `GuideKey` from the same production database used to compile the guide. Do not display the technical key.
- Long names are ellipsized and remain accessible through the full-name tooltip. This is a presentation-only change.

## Instructor experimental observation removal (2026-10-24)
- Removed the abandoned automatic structural Observation implementation end-to-end: Instructor HTTP endpoints, capture-bridge comparison state, native pipe route, extension heartbeat sampling, DOM snapshot before/after event payloads, and dormant Web UI functions/polling.
- Manual primary/secondary target selection, picker, and ordinary action recording remain supported. Existing guide definitions and Learner completion semantics are unchanged. The removed observation API is intentionally no longer supported.

## Web completion target transitions during server refresh (2026-10-24)
- For explicitly authored `target-appeared` and `target-vanished`, the Learner tracks target-scoped DOM mutation revisions and document identity in addition to visible presence. A previously visible target refreshed by a committed action can count as appeared, even when a short disappearance is missed by periodic inspection.
- The adapter latches a detected transition through the stability recheck; a first sample alone never completes a transition. The primary action validation remains required. `target-exists` and `target-not-exists` retain their original DOM-resolution semantics. No application-specific selectors or HTML-content rules are introduced.
